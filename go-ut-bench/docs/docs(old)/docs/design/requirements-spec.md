# ut-bench 需求规格说明（v0.1）

> 状态：Draft（用于本周开发冻结）
> 适用范围：先内部落地，后续开源

## 1. 背景与目标

`ut-bench` 用于横向评测不同大语言模型（LLM）生成单元测试的能力，目标是做成可交互的软件产品，解决以下问题：

- 不同模型生成单测质量缺少统一量化标准。
- 难以在同一执行环境下进行可复现对比。
- 缺少面向工程决策的可视化报告输出。

本阶段目标：

- 本周优先跑通 **Python 端到端评测流程**。
- 文档层面覆盖 Java / Go / C++ 的后续扩展方案。
- 以 TypeScript 为主实现可配置评测软件能力。
- 产出可读、可对比的 HTML 报告与可视化图表。

## 2. 用户与角色

- 评测执行者：配置模型、触发评测、查看运行日志。
- 技术决策者：查看模型横向对比报告，辅助选型。
- 平台维护者：扩展模型接入、维护数据集与指标实现。
- 管理员/高级用户：维护提示词模板、模型参数和数据集元数据。

## 3. 范围定义（Scope）

### 3.1 In Scope（v0.1 必做）

- Python 数据集读取与批量评测。
- 软件界面支持多选模型与多选数据集类型。
- 软件界面支持新增模型配置（名称、Provider、模型标识、鉴权信息引用）。
- 可配置模型调用（不绑定单一模型厂商）。
- 提示词工程能力（系统提示词模板、语言/场景变量替换、版本管理）。
- 指标计算与落盘：
  - 编译通过率（G1）
  - 测试运行通过率（G2）
  - 分支覆盖率（R1）
  - 变异测试得分（C1）
  - 生成耗时（C3）
  - Token 消耗（C2）
- HTML 报告生成（人类可读、支持多模型对比）。
- 报告可视化至少包含：指标矩阵表、雷达图、模型表现排名。

### 3.2 Out of Scope（v0.1 暂不实现）

- Java / Go / C++  端到端执行落地（仅保留设计说明）。
- 复杂评分建模（当前阶段不做固定加权总分）。
- 线上服务化、权限系统、多租户能力。

## 4. 端到端业务流程

1. 在软件中选择数据集与语言（v0.1 为 Python，可多选数据集类型）。
2. 在软件中选择待评测模型列表（可多选），必要时新增模型配置。
3. 选择提示词模板/策略并生成最终提示词。
4. 调用模型生成测试代码。
5. 执行编译与测试运行。
6. 统计覆盖率与变异测试结果。
7. 记录耗时与 Token 数据。
8. 生成结构化结果（JSON）与 HTML 可视化报告。

## 5. 功能需求

### FR-1 数据集管理

- 系统应支持按目录加载评测样本。
- 系统应支持按语言过滤样本。
- 系统应支持按数据集类型多选（如语言、难度、场景）。
- 系统应对无效样本给出明确错误信息并继续处理其他样本。

### FR-2 软件交互能力

- 系统应提供软件化交互界面（至少支持模型与数据集选择、任务启动、结果查看）。
- 系统应支持模型多选、数据集多选。
- 系统应支持新增/编辑模型配置并持久化。

### FR-3 模型调用

- 系统应支持通过配置文件定义模型列表与参数。
- 系统应支持多模型批量评测。
- 系统应记录每次调用的请求元信息（模型名、时间、Token、耗时）。

### FR-4 提示词工程

- 系统应支持提示词模板化（system/user 模板分离）。
- 系统应支持根据语言、任务类型、测试风格注入变量。
- 系统应支持保存提示词版本并可回溯。

### FR-5 指标计算

- 系统应按样本输出六项原始指标。
- 系统应按模型聚合统计（均值、通过率、分位数等）。
- 系统应保留原始明细，便于排查与复核。

### FR-6 报告生成

- 系统应生成 HTML 报告并包含模型横向对比。
- 报告应支持按模型、样本、指标维度查看结果。
- 报告应展示失败样本与失败原因摘要。
- 报告应包含指标矩阵视图（模型 × 指标）。
- 报告应包含雷达图展示模型能力轮廓。
- 报告应提供排名视图（默认按可配置主指标排序，不强制固定加权总分）。

### FR-7 结果存储

- 所有评测产物应输出到 `results/`。
- 至少包含：`raw.json`、`summary.json`、`report.html`、执行日志。

## 6. 非功能需求

### NFR-1 可复现性

- 评测执行环境应尽量统一（推荐 Docker Linux 容器）。
- 相同输入与配置应得到可复核结果。

### NFR-2 可观测性

- 关键步骤必须有日志：模型调用、测试执行、指标计算、报告生成。
- 失败应有可定位信息（命令、退出码、stderr 摘要）。

### NFR-3 可扩展性

- 新增模型应以配置扩展为主，尽量避免改动主流程。
- 新增语言时可复用统一流程骨架（runner/evaluator/reporter）。

### NFR-4 技术栈约束

- 软件主实现语言为 TypeScript。
- 软件交付形态优先为桌面端。
- 代码结构应支持拆分为 UI 层与执行引擎层。
- 若依赖外部评测工具，需通过清晰的适配层封装调用。

## 7. 配置与目录约定

- 模型配置：`benchmark/config/models.yaml`
- 设计文档：`docs/design/*.md`
- 脚本入口：`scripts/setup.sh`、`scripts/run_benchmark.sh`、`scripts/gen_report.sh`
- 评测输出：`results/`

## 8. 验收标准（Definition of Done）

满足以下条件视为 v0.1 达标：

1. Python 样本可完成一轮端到端评测。
2. 报告包含并展示六项指标的模型对比结果。
3. 软件界面可完成模型多选、数据集多选、任务发起。
4. 报告包含矩阵表、雷达图和排名视图。
5. 结果目录可追溯到样本级明细与日志。
6. 文档明确记录未实现项与后续扩展方向。

## 9. 里程碑建议

- M1：需求冻结（本文件评审通过）。
- M2：Python pipeline 跑通（含基础日志与结果落盘）。
- M3：HTML 报告可读可对比。
- M4：补齐 Java / Go / C++ 设计与接入计划。

## 10. 风险与依赖

- 外部模型 API 受限于密钥、额度和速率限制。
- 变异测试耗时较高，需控制样本规模与超时策略。
- 不同模型返回结构可能存在差异，需适配层统一。
- 当前仓库为脚手架状态，部分模块需先完成最小实现。

## 11. 待确认事项

- 首批接入模型清单（建议至少 2 个模型用于对比演示）。
- HTML 报告是否需要导出静态截图或 PDF。
- 桌面端技术路线（Electron 或 Tauri）最终选型。
