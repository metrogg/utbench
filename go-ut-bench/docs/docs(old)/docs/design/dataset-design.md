# 数据集设计

## 1. 设计目标

数据集用于评估不同模型在单元测试生成任务上的表现差异，需满足：

- 跨语言可比：覆盖 Java、Python、Go、C++
- 场景可分层：包含基础函数、边界处理、依赖交互等
- 工程可执行：样本尽量自包含、可被直接读取和生成测试

## 2. 目录结构

```text
dataset/
  java/
  python/
  go/
  cpp/
```

每个语言目录存放待测源码样本，Runner 自动遍历并处理。

## 3. 维度设计

### 3.1 语言维度

- Java
- Python
- Go
- C++

### 3.2 难度维度（通过文件名表达）

- `simple_*`：纯函数或低依赖逻辑
- `boundary_*`：边界值与异常路径
- `interface_mock_*`：接口依赖、Mock 场景
- `complex_dependency_*`：复杂依赖与交互

### 3.3 场景维度

- 工具类/算法类
- 服务或对象协作类
- 外部依赖交互类

## 4. 命名规范

推荐格式：

```text
{complexity}_{language}_{scenario}_{index}.{ext}
```

示例：

- `simple_function_python_simple_function_0.py`
- `boundary_go_boundary_0.go`
- `complex_dependency_cpp_complex_dependency_0.cpp`

## 5. 样本质量要求

- 可读性：核心逻辑清晰，便于模型理解
- 可测试性：存在可断言的输入输出行为
- 代表性：覆盖真实工程常见模式
- 稳定性：尽量避免依赖外部运行环境

## 6. 与 Runner 的契合点

Runner 在处理样本时会使用：

- 文件路径：推断语言类型
- 文件名：提取场景与复杂度上下文
- 源码内容：提取依赖线索并生成 Prompt

因此建议保持命名规范与代码结构稳定。

## 7. 扩展策略

新增样本时建议遵循：

1. 每语言保持难度分布均衡
2. 新增样本不要与已有样本功能完全重复
3. 复杂样本优先补齐当前薄弱维度（如超时高的场景）

## 8. 后续规划

- 引入样本元数据文件（如 JSON）统一记录复杂度、依赖类型
- 增加脚本自动校验样本命名与结构一致性
- 增加更多业务类型（IO、并发、状态机、异常传播）
