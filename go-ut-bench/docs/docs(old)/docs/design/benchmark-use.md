# 多语言单元测试评测集说明

## 一、项目目标

本评测集面向“大模型自动生成单元测试”能力评估而设计，目标是构建一套覆盖多语言、可复现、可扩展、可逐步贴近真实研发场景的评测体系。

当前评测集覆盖以下五种语言：

- Python
- Go
- Java
- C++
- JavaScript

本评测集的核心目标不是简单收集代码样本，而是围绕“大模型在不同复杂度环境下生成单元测试的能力”建立分层评测框架，以支持模型横向比较、评测流水线建设以及后续真实项目验证。

## 二、总体设计思路

本评测集采用“双轨设计”，即为每种语言尽量同时准备两类评测数据：

- `self_contained`：基础评测集
- `module_level`：项目级评测集

这样设计的原因在于，大模型单元测试生成能力不能只在单一场景下衡量。

如果只做单文件评测，虽然结果更稳定、可复现性更强，但无法充分反映模型在真实项目中的表现。  
如果只做项目级评测，虽然更贴近真实研发环境，但执行复杂度高、环境噪声大，不利于统一 benchmark 和模型公平比较。

因此，本项目采用“基础评测 + 项目验证”的组合思路：

- 用基础评测集衡量模型的可控条件下测试生成能力
- 用项目级评测集衡量模型的真实项目适配与落地能力

## 三、两类评测集的含义

### 1. 基础评测集 `self_contained`

基础评测集主要面向单文件评测场景，其设计原则是尽量保证样本自包含、依赖可控、执行稳定。

其主要特点包括：

- 样本相对独立
- 更适合单文件评测
- 更适合统一 prompt 和统一执行流程
- 更适合自动化流水线和大规模模型对比

基础评测集主要回答的问题是：

“当输入是一段相对可控、结构清晰的代码时，大模型能否生成结构完整、断言合理、覆盖充分的单元测试？”

### 2. 项目级评测集 `module_level`

项目级评测集主要面向真实项目模块场景，其设计原则是保留真实工程中的模块上下文和依赖关系。

其主要特点包括：

- 样本来自真实项目模块
- 允许存在包内引用、相对导入、第三方依赖
- 允许存在接口交互、mock 需求与上下文依赖
- 不能简单按孤立单文件方式直接执行

项目级评测集主要回答的问题是：

“当大模型面对真实项目模块时，是否仍然能够理解模块行为、适配项目结构，并生成可执行且有意义的单元测试？”

## 四、样本任务分类

为了避免评测只覆盖“普通函数 happy path”，本评测集统一划分为四类任务：

- `simple_function`
- `boundary`
- `complex_dependency`
- `interface_mock`

其含义如下：

- `simple_function`：关注基础测试生成能力
- `boundary`：关注边界条件、异常值、极端输入等处理能力
- `complex_dependency`：关注依赖理解、上下文分析和复杂逻辑处理能力
- `interface_mock`：关注 mock、替身对象和交互行为测试能力

这种分类方式有助于将模型能力从“能不能写测试”进一步细化为“在哪类任务上更强、在哪类任务上更弱”。

## 五、当前建设情况

### 1. 语言覆盖情况

当前五种语言均已纳入评测体系，且均已具备基础评测集与项目级评测集。

### 2. 当前成熟度

从可执行成熟度来看，目前进展并不完全一致。

- 基础评测集是当前最成熟、最适合统一开跑的部分
- Python 项目级评测已经具备真实恢复与执行示例
- 其余四种语言的项目级数据已经整理完成，但项目恢复、依赖安装、测试注入和 coverage 执行器仍需继续完善

因此，当前最准确的表述不是“五种语言都已经完整支持项目级评测”，而是：

“五种语言都已完成双轨数据组织；基础评测已可统一使用，项目级评测已完成样本定义，其中 Python 已具备真实执行示例，其余语言仍需补齐恢复与执行链路。”

## 六、评测集如何使用

### 1. 基础评测集的使用方式

基础评测集适用于单文件 benchmark。推荐流程如下：

1. 读取样本源码
2. 将源码输入大模型
3. 生成单元测试
4. 落盘测试文件
5. 执行编译、运行和覆盖率采集
6. 汇总通过率、覆盖率、耗时、token 消耗等指标

这一轨道最适合：

- 多模型横向对比
- 自动化流水线验证
- 可复现 benchmark

### 2. 项目级评测集的使用方式

项目级评测集不能直接按单文件方式使用。推荐流程如下：

1. 恢复目标模块所在项目的上下文
2. 安装项目依赖
3. 将目标模块放回原有项目结构
4. 将模型生成的测试放到正确测试目录
5. 在项目环境中执行测试
6. 只统计目标模块的测试结果和 coverage

这一轨道最适合：

- 验证模型在真实项目中的落地能力
- 识别模型在断言语义、上下文理解和依赖适配上的短板
- 作为基础 benchmark 之外的真实性补充

## 七、当前可以支撑的评测结论

基于现有设计，这套评测集可以支持以下几类结论输出：

- 不同模型之间的单元测试生成能力比较
- 不同语言之间的大模型适配差异比较
- 不同任务类别下的能力强弱分析
- 基础环境与真实项目环境下的能力落差分析
- 覆盖率、通过率、测试有效性之间关系的进一步讨论

换句话说，这套评测集既能服务于“做 benchmark”，也能服务于“做分析”。

## 八、使用时需要特别注意的问题

在实际使用和汇报中，需要特别避免以下误区：

### 1. 不能将两类评测混为一谈

基础评测集和项目级评测集面对的是不同难度和不同目标，不能把两者分数直接看成同一尺度。

### 2. 不能把项目级样本按单文件直接执行

项目级样本保留了真实工程依赖，如果脱离项目上下文运行，结果会失真，甚至会误判为模型能力不足。

### 3. 不能只看覆盖率百分比

覆盖率只是结果的一部分，还需要结合：

- 测试是否真正可运行
- 断言是否正确
- 边界条件是否覆盖
- 失败是环境问题还是模型语义问题

### 4. 不能误说五种语言项目级都已完全打通

当前真正具备项目级真实执行示例的是 Python。其他语言的数据组织已经完成，但仍需补齐执行链路。

## 九、当前阶段的核心价值

本评测集当前最重要的价值体现在三个层面：

### 1. 形成了统一的多语言评测框架

过去不同语言往往使用不同格式、不同样本标准，难以统一比较。当前这套评测集已经把五种语言纳入统一框架，并用相同的任务分类组织样本。

### 2. 建立了从“可复现 benchmark”到“真实项目验证”的分层路径

这意味着项目不再停留在“只看单文件表现”，而是已经具备进一步向真实项目落地扩展的结构基础。

### 3. 为后续评测流水线和模型对比提供了稳定输入

无论是继续开发单文件评测脚本，还是补全项目级执行器，这套评测集都已经提供了清晰的输入定义和评测边界。

## 十、建议的后续推进顺序

结合当前状态，建议后续工作按以下顺序推进：

1. 优先基于基础评测集完善五种语言统一评测流水线
2. 将 Python 项目级评测进一步标准化、批量化
3. 迁移 Python 的恢复与执行思路到 Go 和 JavaScript
4. 最后补齐 Java 与 C++ 的项目恢复与执行能力

这样的推进顺序兼顾了可执行性、结果产出速度与整体工程复杂度。

## 十一、汇报时可直接使用的总结表述

可以将本评测集概括为：

“本项目构建了一套覆盖 Python、Go、Java、C++ 与 JavaScript 的多语言单元测试评测集，并采用双轨设计：基础轨道面向可复现的单文件 benchmark，项目级轨道面向真实项目模块评测。当前基础轨道已可用于统一模型比较，项目级轨道已完成样本组织，其中 Python 已具备真实恢复执行示例，其余语言正在继续补齐项目恢复与执行链路。” 

## 十二、结论

这套评测集的核心意义，不在于单纯提供代码样本，而在于把“大模型单元测试生成能力”拆分为两个层次进行评估：

- 一个层次强调可复现、可比较、可自动化
- 一个层次强调真实项目环境中的可落地性

正是这种分层设计，使得评测结果既能用于模型 benchmark，也能用于分析模型在真实工程场景中的能力边界。
