# 评测指标定义
## 一、指标体系总览

本项目采用两层指标体系：Gate（门槛指标）+ Core（核心指标）。

- **Gate 指标**：门槛过滤，不达标直接淘汰，不进入核心评测
- **Core 指标**：核心展示与排序参考，不计算固定加权总分

### 统一执行环境（强制）

为保证跨语言一致性与可复现性，**所有指标统一在 Docker Linux 容器内执行**，主机仅负责调度。

- Windows 主机不直接运行变异工具（例如 Python 的 `mutmut`）
- Java/C++ 依赖工具链（Maven/PIT/Mull/GoogleTest）统一放入容器镜像
- 评测结果（日志、覆盖率、变异报告）统一输出到挂载卷 `results/`

### 展示与排序原则

- 本版本不使用固定加权总分。
- Gate 指标用于质量门槛过滤与分层展示。
- Core 指标用于横向对比与排序参考。
- 保留原始指标值，避免过早引入单一评分模型导致误导。

***

## 二、Gate 指标（门槛过滤）

### G1 编译通过率

| 项目       | 内容                  |
| -------- | ------------------- |
| **定义**   | AI 生成的测试代码能否成功编译    |
| **公式**   | `编译成功数 / 总数 × 100%` |
| **阈值**   | ≥ 70%               |
| **淘汰规则** | 未达标 → 直接淘汰          |

**实现方案（容器内）**

| 语言     | 工具          | 命令                                 |
| ------ | ----------- | ---------------------------------- |
| Java   | javac       | `javac -cp <classpath> Test*.java` |
| Python | py\_compile | `python -m py_compile test_*.py`   |
| Go     | go build    | `go build ./...`                   |
| C++    | clang++     | `clang++ -std=c++17 -c test_*.cpp` |

**数据采集**：解析编译命令退出码，0 为成功，非 0 为失败。

**注意事项**

- Java 需要配置正确的 classpath，包含被测代码和测试框架依赖
- Python 需要确保第三方库已安装（pytest、mock 等）
- C++ 必须使用 Clang（Mull 变异测试要求）

***

### G2 运行通过率

| 项目       | 内容                     |
| -------- | ---------------------- |
| **定义**   | 编译通过的测试用例能否全部运行通过      |
| **公式**   | `运行通过数 / 编译成功数 × 100%` |
| **阈值**   | ≥ 90%                  |
| **淘汰规则** | 未达标 → 直接淘汰             |

**实现方案（容器内）**

| 语言     | 工具          | 命令                                                             |
| ------ | ----------- | -------------------------------------------------------------- |
| Java   | JUnit 5     | `mvn test` 或 `java -jar junit-platform-console-standalone.jar` |
| Python | pytest      | `pytest test_*.py -v`                                          |
| Go     | go test     | `go test ./... -v`                                             |
| C++    | Google Test | `./test_binary --gtest_color=yes`                              |

**数据采集**：解析测试框架输出，统计 Pass / Fail / Error / Timeout 状态。

**注意事项**

- 所有测试运行需设置超时阈值（建议 30 秒/测试用例），超时计入失败
- 区分 Fail（断言失败）和 Error（运行异常），但在 G2 中统一计为不通过
- Crash（进程崩溃）单独记录，作为严重问题标记

## 三、Core 指标（核心展示）

### C1 变异查杀率

| 项目     | 内容                                                  |
| ------ | --------------------------------------------------- |
| **定义** | AI 生成的测试能否检测到源代码中被故意注入的逻辑错误                         |
| **公式** | `KILLED / (KILLED + SURVIVED + NO_COVERAGE) × 100%` |
| **评分参与** | 不参与固定加权总分（用于展示与排序参考）                         |
| **阈值** | 及格 ≥ 30%，良好 ≥ 50%，优秀 ≥ 70%                          |

**变异体状态说明**

| 状态           | 含义                     |
| ------------ | ---------------------- |
| KILLED       | 测试发现了变异（测试失败），说明测试有效   |
| SURVIVED     | 测试未发现变异（测试仍通过），说明测试有漏洞 |
| NO\_COVERAGE | 变异所在代码行未被测试覆盖          |
| TIMED\_OUT   | 测试超时（计入 KILLED）        |

**实现方案（容器内）**

| 语言     | 工具           | 命令                                             | 输出格式         |
| ------ | ------------ | ---------------------------------------------- | ------------ |
| Java   | PIT (pitest) + pitest-junit5-plugin | `mvn org.pitest:pitest-maven:mutationCoverage` | mutation.xml |
| Python | mutmut       | `mutmut run`                                   | JSON 结果      |
| Go     | go-mutesting | `go-mutesting ./...`                           | 控制台输出        |
| C++    | Mull         | `mull-runner-18 test_binary`                   | SQLite 数据库   |

**数据采集**

```python
# 伪代码
def calculate_mutation_score(mutations):
    killed = count(m for m in mutations if m.status in ['KILLED', 'TIMED_OUT'])
    survived = count(m for m in mutations if m.status == 'SURVIVED')
    no_coverage = count(m for m in mutations if m.status == 'NO_COVERAGE')

    return killed / (killed + survived + no_coverage) * 100
```

**注意事项**

- 变异测试耗时较长，建议对每个源文件单独运行，支持并行
- PIT 和 mutmut 的变异算子覆盖范围略有差异，跨语言对比时需注意
- Mull 必须使用 Clang 编译器，GCC 不支持
- TIMED\_OUT 通常说明变异导致了死循环，应计为 KILLED
- Java 使用 JUnit5 时需显式引入 `pitest-junit5-plugin`

### C2 Token 成本

| 项目     | 内容                                                       |
| ------ | -------------------------------------------------------- |
| **定义** | AI 生成单元测试所消耗的 API 调用费用                                   |
| **公式** | `prompt_tokens × 输入单价 + completion_tokens × 输出单价`（单位：美元） |
| **评分参与** | 不参与固定加权总分（用于展示与排序参考）                              |
| **阈值** | 无固定阈值，按相对排名评分                                            |

**模型单价参考**

| 模型                | 输入 ($/1M tokens) | 输出 ($/1M tokens) |
| ----------------- | ---------------- | ---------------- |
| GPT-4o            | 2.50             | 10.00            |
| Claude 3.5 Sonnet | 3.00             | 15.00            |
| DeepSeek-V3       | 0.27             | 1.10             |
| 混元                | 待补充              | 待补充              |

> 注：模型价格会调整，评测时需记录实际使用的单价版本。

**数据采集**：从模型 API 响应的 `usage` 字段提取 `prompt_tokens` 和 `completion_tokens`。

**归一化方式**

```
得分 = (1 - 实际成本 / 同批最大成本) × 100
```

成本最低的模型得 100 分，成本最高的得 0 分。

**注意事项**

- 同一个源文件需要多次调用（多次生成取最优）时，Token 消耗应累加
- 如果模型支持缓存/复用，需按实际计费口径统计
- 成本仅计算模型调用费用，不包含评测工具运行的计算资源

***

### C3 生成耗时

| 项目     | 内容                                         |
| ------ | ------------------------------------------ |
| **定义** | AI 生成单元测试从请求发起到返回结果的总耗时                   |
| **公式** | `Σ(每个样本生成耗时) / 样本数`（单位：ms）                 |
| **评分参与** | 不参与固定加权总分（用于展示与排序参考）         |
| **阈值** | 无固定阈值，按相对排名评分                              |

**数据采集**：在模型调用前后记录时间戳，统计单样本耗时，并汇总 `avg/p50/p95`。

**归一化方式**

```
得分 = (1 - 实际耗时 / 同批最大耗时) × 100
```

耗时最低的模型得 100 分，耗时最高的得 0 分。

**注意事项**

- 必须在同一网络环境和并发配置下比较耗时，避免环境噪音
- 建议同时记录 `p50/p95`，防止平均值掩盖长尾延迟
- 多次调用（重试/多轮生成）时，耗时需累计

## 四、排序与展示（无固定总分）

### 排序流程

```
Step 1: Gate 检查
├── G1 编译通过率 ≥ 70%？
└── G2 运行通过率 ≥ 90%？
    ↓ 全部 PASS
Step 2: Core 对比
├── C1 变异查杀率
├── R1 分支覆盖率
├── C2 Token 成本
└── C3 生成耗时
    ↓
Step 3: 排序
默认按「G1/G2 门槛通过」+「C1 优先」+「R1/C3/C2 次级规则」排序
```

### 示例

| 模型   | G1 | G2 | C1 (%) | R1 (%) | C2 (美元) | C3 (ms) | 展示结论 |
| ---- | -- | -- | ------ | ------ | ------- | ------ | ---- |
| 模型 A | ✅  | ✅  | 65%    | 62%    | 0.08    | 1800   | 门槛通过，核心表现较均衡 |
| 模型 B | ✅  | ✅  | 55%    | 68%    | 0.03    | 1200   | 门槛通过，成本与时延优势明显 |
| 模型 C | ✅  | ✅  | 72%    | 40%    | 0.95    | 3200   | 门槛通过，查杀强但成本较高 |
| 模型 D | ❌  | —  | —      | —      | —       | —      | 门槛未通过，单列展示 |

## 五、核心指标（续）

### R1 分支覆盖率（核心展示指标）

| 项目     | 内容                     |
| ------ | ---------------------- |
| **定义** | 测试对被测代码的分支覆盖程度         |
| **公式** | `已覆盖分支数 / 总分支数 × 100%` |
| **评分参与** | 不参与固定加权总分（用于展示与排序参考） |

**实现方案（容器内）**

| 语言     | 工具            | 命令                                                 |
| ------ | ------------- | -------------------------------------------------- |
| Java   | JaCoCo        | `mvn jacoco:report`                                |
| Python | pytest-cov    | `pytest --cov=src --cov-report=term-missing`       |
| Go     | go tool cover | `go test -coverprofile=coverage.out`               |
| C++    | llvm-cov      | `llvm-cov show ./test_binary -source-file src.cpp` |

**诊断逻辑**

| 变异查杀率 | 分支覆盖率 | 问题诊断          |
| ----- | ----- | ------------- |
| 低     | 低     | 测试没跑到，漏测      |
| 低     | 高     | 测试跑到了但断言弱，质量差 |
| 高     | 低     | 偶然通过，实际覆盖不足   |
| 高     | 高     | 测试质量好         |

**注意事项**

- 分支覆盖率是"量"的衡量，变异查杀率是"质"的衡量
- 覆盖率 100% 不代表测试有效（可能都是弱断言）
- 变异查杀率 70% + 分支覆盖率 40% 说明有侧重的覆盖，但没有充分验证
