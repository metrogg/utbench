# 评估函数单元测试价值

公正地评价指定的被测函数是否值得测试，评估基于统一标准，结果稳定可重复

## 评估流程

1. 读取并理解指定的每个被测函数逻辑
2. 分别从 _重要程度_ 、 _可测试性_ 、 _测试副作用_ 三个维度对指定的每个被测函数进行 A B C 评级
3. 对指定的每个函数综合三个维度评级评估是否值得对指定被测函数进行单元测试
   1. 如果有 C 评级一般不进行单元测试
   2. 除非用户有别的要求，否则没有 C 评级就可以进行单元测试

## 输出格式

使用 Markdown 格式输出结果，对每个指定的函数分别包含三小节说明：

1. 每个分维度评级结果和评级依据描述
2. 综合评估结果和依据描述

最后再包含一个 JSON 代码段， JSON 代码段中是包含以下字段的 JSON 对象的列表。每个被评估的函数一项。

- `funcName` (string) 函数名
- `importance` (string) 重要程度评级， `A` `B` 或 `C`
- `testability` (string) 可测试性评级， `A` `B` 或 `C`
- `sideEffect` (string) 测试副作用评级， `A` `B` 或 `C`
- `isWorth` (bool) 是否值得进行单元测试
- `message` (string) 评估结果的一个简短描述

比如

```json
[
  {
    "funcName": "Example1",
    "importance": "A",
    "testability": "B",
    "sideEffect": "A",
    "isWorth": true,
    "message": "重要程度较高的库函数，建议单测"
  },
  {
    "funcName": "Example2",
    "importance": "A",
    "testability": "B",
    "sideEffect": "C",
    "isWorth": false,
    "message": "测试过程中会写系统文件，副作用高，不适合单测"
  }
]
```

## 关于读取代码的要求

- 获取被测代码不一定需要读取整份代码文件，如果只是获取被测函数可以通过 Grep 查找函数定义所在行，然后从函数定义所在行往下每次读取 200 行，直到读取到函数末尾
- 只有在确定需要获取其他代码时才读取其他代码，每次读取不超过 1000 行，可以分多次读取

## 重要程度评级方法

评级结果分为 A 、 B 或 C ，其中 A 表示重要， C 表示不重要， B 是中性评价

原则：函数功能越基础、潜在被调用深度越深、潜在被调用次数越多就越重要

参考基准：

- 库函数可评为 A
- 入口函数一般不高于 B ，如程序入口、 HTTP RPC 等接口处理函数

## 可测试性评级方法

评级结果分为 A 、 B 或 C ，其中 A 表示可测试性高且易于测试， C 表示可测试性低且难于测试， B 是中性评价

原则：功能越单一、依赖越少、输入越易于构造、输出越易于验证的函数可测试性越高

参考基准：

- 输出不可通过函数返回语句获取的一般不高于 B
- 存在无法 mock 的依赖的评级一般不高于 B
- 存在无法通过构造输入覆盖的分支的评级一般不高于 B
- 存在因关键依赖无法 mock 主流程无法进行的评为 C

## 测试副作用评级方法

评级结果分为 A 、 B 或 C ，其中 A 表示副作用低， C 表示副作用高， B 是中性评价

原则：测试过程无法限制在测试程序内部的外部影响越少副作用就越低。需要从外部影响性质和限制影响可行性两方面评估。

常见的令人不悦的外部影响包括：

- 调用外部 HTTP 、 RPC 等接口
- 访问 MySQL 等外部数据库
- 读写文件操作

常见的限制影响的方式：

- 通过 mock 产生外部影响的函数使外部影响不真正发生
- 通过将调用外部 HTTP 接口的地址改为调用测试程序内测试 HTTP 服务地址使 HTTP 请求不发送到程序外部
- 使用 SQLite 代替 MySQL 进行测试
- 在系统临时文件目录创建测试目录，控制读写文件操作限制在测试目录内

参考基准：

- 存在至少一个无法限制的外部影响就评级为 C
- 不存在外部影响的评级为 A
- 存在外部影响的根据限制手段难易程度在 B 上下评级
